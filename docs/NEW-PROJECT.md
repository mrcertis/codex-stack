# Начало нового проекта

Напишите: «Давай сделаем сайт для [название проекта]» или «Хочу бота для записи
клиентов». Агент сам выбирает инструменты и задаёт вопросы о продукте.

Порядок: идея → подготовка локальных skills → интервью → требования → дизайн
при необходимости → документы и код → проверка. Исправление небольшого бага
не запускает этот процесс заново.

## Что происходит автоматически

При установке стека глобально размещается [stack-start](../skills/stack-start/SKILL.md).
Его описание подходит обычным запросам на создание продукта. SessionStart и
UserPromptSubmit напоминают агенту прочитать этот skill при старте нового проекта.

Агент определяет папку проекта и запускает поставляемый prepare_project.py.
Тот ставит **локально и сразу** grill-with-docs, grilling, domain-modeling и
Impeccable. Установка Impeccable не требует заранее выбранного интерфейса.
Источник интервью — [mattpocock/skills](https://github.com/mattpocock/skills),
дизайна — [Impeccable](https://impeccable.style/docs/).

Сам hook не скачивает пакеты в произвольную открытую папку. Он передаёт маршрут
агенту; агент выполняет подготовку в целевом проекте из пользовательского запроса.
Если папка ещё не определена, агент сначала определяет её. Для чтения чужого
репозитория и небольших правок набор автоматически не устанавливается.

## Почему не требуется команда skill

Upstream grill-with-docs — короткая explicit-only обёртка над grilling и
domain-modeling. Автоматический stack-start сам объединяет эти два skill в тот же
процесс. Он не меняет upstream-файл и не просит человека писать специальную команду.
Если каталог skills текущей сессии ещё не обновился, агент читает локальные файлы
непосредственно; обнаружение и доверие к новым hooks проверяются отдельно.

## Что появляется в проекте

1. **Интервью.** Grilling уточняет цель, пользователей, сценарии, границы и спорные
   решения. Агент самостоятельно проверяет факты, доступные в коде и документации.
   Реализация начинается после согласованного понимания.
2. **Требования.** `docs/brief.md` либо уже принятый документ требований: цель,
   пользователи, сценарии, ограничения, что не входит, критерии готовности.
   `CONTEXT.md` от domain-modeling — словарь предметной области, не замена brief.
   ADR создаются по необходимости для существенных решений.
3. **Дизайн, если есть UI.** Impeccable уже установлен. Агент читает skill,
   запускает его context.mjs согласно текущей инструкции,
   переиспользует интервью в init и уточняет только пробелы. `init` пишет PRODUCT.md.
   Для нового визуального мира выбирается концепция и согласуется направление до
   реализации. `shape` сам по себе не означает готовую реализацию.
4. **Документы и код.** Технический план опирается на требования и выбранное
   направление. Большую работу можно вести через GSD, сохраняя результаты интервью.
   DESIGN.md и sidecar описывают построенный визуальный мир по завершающему
   playbook Impeccable; не создавайте фиктивный DESIGN.md после init.
5. **Проверка.** Критерии продукта, нужные тесты, реальные состояния интерфейса
   и размеры экрана. Emil уточняет взаимодействие, Agentation собирает замечания.

Для backend/CLI без интерфейса дизайн-процесс пропускается, skill остаётся локально.
Полная Wiki-компиляция
не является обязательной частью каждого старта; запись в Wiki требует запроса.
